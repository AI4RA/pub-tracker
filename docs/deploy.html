Track your institution's publications

The demo finds each PI's most recent paper. Deployed, Pub Tracker does what a research office actually needs: it keeps a complete, self-updating record of every paper your PIs publish. You run it in a private copy of this repository. Each week GitHub Actions gathers every PI's papers from OpenAlex, Semantic Scholar, PubMed and ORCID. Each paper is recorded once, however many sources and versions describe it. Anything new is added to a spreadsheet your office can review, and you get a notice.

You're welcome to take the template and make it your own. We just ask that you keep the attribution.

1. What you get

  • data/pis.xlsx: your PI list, kept in the repository so it is always there for the next run. Edit it whenever people join or leave.
  • data/tracker.db: a SQLite database, the permanent record. It holds every paper, each with a stable Paper ID of its own, and a ledger of every identifier ever seen for it: each source's own ID (OpenAlex, PubMed, ORCID, Semantic Scholar), its DOIs and its title. A paper is recognised by any of these, so papers without a DOI are tracked too, and a paper is never added twice, however late a source indexes it. The database also remembers your review decisions and logs every run.
  • data/papers.xlsx: rebuilt from the database each run, for your office to read and review. It has four sheets:
    • Papers: one row per PI + paper, with a linked title, date, journal, DOI, other versions (such as the preprint of a published article), which sources have it, a confidence level, and the date it was first seen.
    • Possible duplicates: pairs that might be the same paper, for you to decide.
    • PIs: each PI's ORCID, paper count, newest paper and last result.
    • About: how to review, and what the columns mean.
  • A weekly run (Mondays by default) that updates both files and commits them back, so the repository history shows what changed each week.
  • A notice of new papers, and of tracked preprints that have now been published: a GitHub issue that GitHub emails to whoever you assign. Ordinary email over SMTP is optional.

Only papers count: articles, preprints, conference papers, reviews, books, chapters, reports and theses. Datasets, software, posters and talks are left out. The first run is a baseline, so it records everything without sending a notice. A PI you add later is baselined the same way, so you aren't sent their whole back catalogue.

2. Make a private copy

Your copy should be private, because it holds your PI list. GitHub doesn't allow a fork of a public repository to be private, so use the template instead:

  1. Sign in to GitHub and open github.com/AI4RA/pub-tracker.
  2. Click Use this template → Create a new repository.
  3. Choose the owner (your institution's GitHub organization, or your own account), give it a name such as pub-tracker-isu, and select Private.
  4. Click Create repository.

Your copy gets the tracker, the website code, and both workflows. The website's deploy workflow skips itself in a private repository, so you don't need GitHub Pages; your team can keep using the public site for one-off lookups.

3. Add your PI list

  1. Make a spreadsheet with one row per PI. You need a name column (Last, First, First Last, or separate first and last name columns). An Institution column and ORCID iDs make matching much more reliable for common names. data/pis.example.csv shows the shape.
  2. Save it as pis.xlsx (or pis.csv).
  3. In your repository, open the data folder, click Add file → Upload files, drop the file in, and click Commit changes.

To change the list later, upload a new pis.xlsx the same way. It replaces the old one.

If every PI is at one institution, you can leave the Institution column out and set the DEFAULT_INSTITUTION variable instead (next step).

4. Add API keys as secrets

Keys go in repository secrets, never in a file in the repository. Secrets are encrypted, hidden in logs, and passed only to the workflow. In your repository go to Settings → Secrets and variables → Actions.

On the Secrets tab, click New repository secret for each key you have:

Secret nameWhat it isNeeded?
OPENALEX_API_KEYFree key from openalex.org (make an account, verify your email, copy the key from Settings → API key).Strongly recommended. Without it, GitHub's runners share OpenAlex's small keyless budget with everyone else on GitHub's network, so runs will often find OpenAlex already exhausted.
S2_API_KEYSemantic Scholar key, requested on their API form. Approval can take weeks.Recommended. Without it, Semantic Scholar is often throttled; the run carries on with the other sources.
NCBI_API_KEYInstant, from your NCBI account settings → API Key Management.Optional. Raises PubMed from 3 to 10 requests a second.

On the Variables tab (these aren't secret), you can set:

Variable nameExampleWhat it does
NOTIFY_GITHUB_USERSswright,nate-laymanGitHub usernames to assign the "new papers" issue to. GitHub emails them. They need access to the repository.
DEFAULT_INSTITUTIONIdaho State UniversityUsed for any PI whose row has no institution.
CONTACT_EMAILresearch-office@isu.eduSent to OpenAlex and PubMed as the contact they ask heavy users for.
SOURCESopenalex,pubmed,orcidWhich sources to use (default: all four, openalex,s2,pubmed,orcid).
NOTIFY_MAX_AGE_DAYS365Only papers published in this many days are announced. Older papers that a database indexes late are still added to the list, but without a notice. Default 365.

Why not a .env file? A file in the repository is readable by anyone with access to it, ends up in its history, and is easy to leak. A .env file is only for running the tracker on your own computer (see below), and it is already excluded from Git by .gitignore.

5. Choose who hears about new papers

Option A: a GitHub issue (default, no mail setup)

When a run finds new papers, it opens an issue titled, for example, "3 new papers (2026-11-16)", listing each paper by PI with a link, journal, date and the sources that found it. Set NOTIFY_GITHUB_USERS and GitHub emails the assignees, as long as their notification settings send email for assignments (the default). Anyone watching the repository gets it too. Close the issue once you've looked.

This needs nothing from your IT office: no mail server, no app password.

Option B: ordinary email over SMTP (optional)

To send a regular email as well, add these secrets. The email step does nothing until SMTP_HOST and NOTIFY_EMAIL are both set.

SecretExample
SMTP_HOST / SMTP_PORTsmtp.gmail.com / 587
SMTP_USER / SMTP_PASSWORDThe sending account and its password (for Gmail, an app password)
SMTP_FROMPub Tracker <tracker@example.org> (defaults to SMTP_USER)
NOTIFY_EMAILWho to send to; separate several with commas

Many university Microsoft 365 tenants turn off password-based SMTP sending. If yours does, either use Option A, ask IT for an SMTP relay or service account, or use a mail service with SMTP access (Gmail with an app password, SendGrid, Mailgun and others).

6. Run it the first time

  1. Open the Actions tab of your repository. If GitHub asks, click I understand my workflows, go ahead and enable them.
  2. Choose Track PI papers on the left, then Run workflow → Run workflow.
  3. Click into the run to watch the log. Each PI gets a line such as [12/80] Wright, Stephen: 64 records orcid:found openalex:found pubmed:found s2:none. A run of 100 PIs usually takes 5 to 15 minutes.
  4. When it finishes, data/tracker.db and data/papers.xlsx appear in the repository. Click papers.xlsx and choose Download raw file to open it in Excel.

The first run is the baseline: it fills the list and sends no notice. That's the moment to review it. From then on, each scheduled run reports only papers that weren't there before.

7. Review duplicates and remove papers

Pub Tracker decides on its own when records are clearly the same paper: the same DOI, or the same title within a year (which is how a preprint and its published version are linked). When it isn't sure, for example near-identical titles or the same title several years apart, it doesn't guess. It lists the pair under Possible duplicates for you. Expect most of this review after the first run; after that it's occasional.

To review, download the latest data/papers.xlsx, make your changes, and upload it back to data/ (Add file → Upload files, replacing the old one). Changes apply on the next run.

To…Do this in papers.xlsx
Merge two papersUnder Possible duplicates, write same in the Decision column. Paper B is merged into Paper A, and its DOI is kept under Other versions. Or, on the Papers sheet, give both rows the same Paper ID.
Keep two papers apartWrite different in the Decision column. The pair won't be flagged again.
Remove a paperDelete its row on the Papers sheet. It's remembered as ignored, so it never comes back, even if a source keeps listing it (for example, a namesake's paper).

Only edit the latest papers.xlsx. Each export carries an Export ID (on its About sheet). If you upload an older copy after a newer run, Pub Tracker won't apply its row deletions, so papers found in between can't be lost by mistake. Decisions on possible duplicates are still applied. Every version is in the repository history if you need to undo something.

8. Change the schedule

The schedule is the cron line in .github/workflows/track.yml. Edit it on GitHub (pencil icon) and commit. Times are in UTC.

cronRuns
0 13 * * 1Mondays at 13:00 UTC (the default)
0 13 * * *Every day at 13:00 UTC
0 13 1 * *The 1st of every month

You can always run it by hand from the Actions tab too.

9. Limits and costs

  • GitHub Actions. Private repositories get a monthly allowance of free minutes (2,000 on GitHub Free, 3,000 on Team). A weekly run of 100 to 200 PIs uses roughly 40 minutes a month.
  • OpenAlex. With a free key you have $1 of usage a day. Each PI costs about a tenth of a cent, so roughly 800 PIs a run.
  • Semantic Scholar. About one request a second. Without a key it is the source most likely to be switched off mid-run when busy.
  • If a source hits its limit, the run switches that source off for the rest of the run and carries on with the others. The PIs sheet records it, and the next run fills in anything missed. No papers are ever removed because a source was unavailable.

10. Where the data goes

  • Your PI list, the database and the spreadsheet live in your private repository on GitHub, under your organization's account.
  • Runs happen on GitHub's servers (Actions runners), which send each PI's name, institution and ORCID iD to the public databases you enable, the same as the website does from a browser.
  • Nothing goes to AI4RA, the University of Idaho, Idaho State University, or anyone else. Your copy has no connection back to the original repository.
  • API keys are stored as encrypted GitHub secrets and are sent only to the service that issued each one.

11. Getting updates

A copy made from a template doesn't follow the original automatically. To pull in later fixes, from a clone of your copy:

git remote add upstream https://github.com/AI4RA/pub-tracker.git
git fetch upstream
git merge upstream/main --allow-unrelated-histories   # first time only needs the flag
git push

Your data/ files aren't in the original, so they won't conflict.

12. Running it on your own computer

You can also run the tracker without GitHub Actions. You need Node.js 22.13 or newer (24 recommended), which includes SQLite.

git clone https://github.com/YOUR-ORG/pub-tracker-isu.git
cd pub-tracker-isu
npm ci --prefix tracker
cp data/pis.example.csv data/pis.csv     # or put your own data/pis.xlsx here
node --env-file=.env tracker/track.mjs   # updates data/tracker.db and data/papers.xlsx

Put your keys in a file named .env in the repository folder. It is excluded from Git, so it never gets committed:

OPENALEX_API_KEY=...
S2_API_KEY=...
NCBI_API_KEY=...
CONTACT_EMAIL=you@example.org
DEFAULT_INSTITUTION=Idaho State University

Leave out --env-file=.env if you have no .env file. New papers are written to data/new-papers.md. To look inside the database, any SQLite tool works, such as DB Browser for SQLite; the tables are papers, ledger, kept_apart, pis and runs.

13. Troubleshooting

The workflow doesn't run on schedule.
Check that Actions is enabled (Settings → Actions → General) and that the workflow file is on the default branch. Scheduled runs can start a few minutes late when GitHub is busy.
"Permission denied" or 403 when saving the list.
Your organization may limit what workflows can do. In Settings → Actions → General → Workflow permissions, choose Read and write permissions, or ask an organization owner to allow it.
No issue was opened.
Issues must be enabled (Settings → General → Features → Issues), and each name in NOTIFY_GITHUB_USERS must have access to the repository. A run that finds nothing new doesn't open an issue.
A source shows "skipped" or "limit reached" on the PIs sheet.
That source ran out of quota partway through. Add its key as a secret, or run less often. The next run catches up.
My edits to papers.xlsx weren't applied.
The run log says so when the uploaded file isn't the latest export. Download the current papers.xlsx, redo the edits, and upload it again.
A paper is attributed to the wrong person.
Common names are the hard case. Add the PI's ORCID iD to pis.xlsx; that gives an exact match in ORCID, OpenAlex and Semantic Scholar. Rows marked Low confidence are worth checking, and you can delete any that aren't theirs.

14. Make it your own, with credit

You're welcome to use the template, rename it, restyle it, change how it matches people, add sources, and run it for your institution. That's what it's for. Pub Tracker is open source under the Apache License 2.0, and all we ask in return is attribution:

  • Keep the NOTICE and LICENSE files in your copy. The license requires this whenever you share the code or something built from it.
  • If you publish a site, a report or a tool built on it, include a line such as: "Based on Pub Tracker by Nathan Layman (University of Idaho) and Stephen Wright (Idaho State University), an AI4RA project supported by NSF award 2427549."
  • To cite it in a paper or report, use CITATION.cff (GitHub's Cite this repository button formats it for you).

Improvements are welcome back as pull requests to AI4RA/pub-tracker. Please don't include your PI list or results in one.
